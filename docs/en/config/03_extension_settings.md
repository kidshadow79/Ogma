## Priority principle

Each extension can have a JSON file in `data/` that **takes priority over Python default values** at runtime. This file is the source of truth for a user cloning the repository.

At startup, the extension reads its configuration JSON. If the file doesn't exist, the Python `DEFAULT_*` constants take over. But if the JSON is present, it overrides the Python values.

## Commit synchronization rule

When an `extensions/*/config*.py` file is modified, the corresponding JSON in `data/` must be committed in the same push. A new user cloning OGMA loads the JSON, not the Python constants.

```bash
git status                          # Check modified data/ JSON files
git add data/[extension]_settings.json
git commit -m "sync: data/ JSON aligned with Python config"
```

---

## Typical extension config file structure

```json
{
  "enabled": true,
  "version": "2.1",
  "settings": {
    "param1": "value",
    "param2": 42
  }
}
```

The `enabled` field is consistently present and controls whether the extension is active.

---

## Output data vs configuration

Some JSON files in `data/` are **outputs** generated by extensions (e.g. `ego_compiled.json`, `journal_reves.json`) and not configurations to edit manually. The distinction matters: manually modifying these files can corrupt the extension's state.
