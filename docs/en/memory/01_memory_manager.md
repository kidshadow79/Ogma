## What it is

OGMA's memory is not a simple notes file. It is a hybrid system combining a structured database (SQLite) and a semantic search index (FAISS). Together, they allow the AI to retrieve relevant memories not just by keywords, but by meaning — even if the user does not remember the exact terms used in the conversation where the memory was created.

---

## Architecture: SQLite + FAISS

**SQLite** stores memories as structured rows. Each memory contains its original text, its type (affective, conceptual, sensory, event), a title, a summary, a valence (positive/negative/neutral), a calculated impact score, and various metadata enriched by the Archivist at creation time.

**FAISS** (Facebook AI Similarity Search) maintains a parallel vector index. Each memory has a numeric vector — its "semantic fingerprint" — generated by the `EmbeddingController`. FAISS finds in milliseconds the memories whose meaning is closest to a query, even if phrased differently.

These two databases are kept in sync: when a memory is added to SQLite, its vector is added to FAISS with a matching identifier. The `id_to_faiss` and `faiss_to_id` dictionaries maintain correspondence between the two systems.

---

## Thread safety

FAISS is not thread-safe by design. `MemoryManager` uses two distinct locks:

- `_faiss_lock`: protects all operations on the FAISS index (adding vectors, searching)
- `_mapping_lock`: protects the id↔FAISS position mapping dictionaries

Every FAISS operation must happen inside a `with self._faiss_lock:` block.

---

## Adding a memory — `add_memory()`

Adding a memory is a multi-step process:

1. **Redundancy check**: first, the system generates an embedding for the new text and compares it to existing memories. If a very similar memory already exists (similarity ≥ threshold, default 92%), the addition is refused. This prevents saturating memory with near-duplicate entries.

2. **Archivist enrichment**: the raw text is sent to the Archivist, which turns it into a structured memory (JSON) with impact scoring, type, title, summary, affective resonances, and an analytical comment.

3. **Embedding generation**: the text is converted to a vector by the `EmbeddingController`.

4. **Dual write**: the memory is inserted into SQLite and the vector is added to FAISS.

---

## Searching memories — hybrid pipeline

The search combines three signals:

| Signal | Weight | What it measures |
|---|---|---|
| FAISS (semantic) | 60% | Meaning proximity between query and memories |
| FTS5 (keywords) | 40% | Exact term presence in memory texts |
| Exact match | +20% bonus | Query words found in title/summary |

The query is first cleaned (personal pronoun expansion, keyword extraction) to improve embedding quality. Results from both engines are merged by weighted score, and the top `k` memories are retrieved from SQLite.

The Archivist then reads these memories and generates a **contextual summary** — a short, relevant note that distills what is pertinent to the question asked. This note is what gets injected into the main AI's context, not the raw memories themselves.

---

## Deletion protection

`delete_all_memories()` creates an automatic backup of the SQLite database in `data/memory/backup/` before any deletion. Deleting a single memory (`delete_memory()`) removes the entry from SQLite but does not rebuild the FAISS index — that is handled by the rebuild procedure (`rebuild_faiss_safe.py`).

---

## Initialization and loading

At startup, `MemoryManager`:
1. Creates or opens the SQLite database (with automatic migration if columns are missing)
2. Initializes an empty FAISS index (`IndexFlatL2` — exact search, suitable for moderate volumes)
3. Loads all existing embeddings from SQLite and reinjects them into FAISS

This step may take a few seconds if the database contains many memories.
