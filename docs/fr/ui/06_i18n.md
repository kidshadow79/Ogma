# Internationalisation (i18n)

**Source vérifiée** : `utils/i18n.py`, `data/i18n/` (structure observée)

---

## Architecture

OGMA supporte deux langues d'interface : français (`fr`) et anglais (`en`). La langue active est lue depuis `data/settings.json` → clé `ui_lang`. Les chaînes traduites sont dans des fichiers JSON séparés : `data/i18n/ui_fr.json` et `data/i18n/ui_en.json`.

---

## API principale : `t(key)`

La fonction `t(key)` est le point d'accès unique à toutes les chaînes de l'interface. Elle :

1. Lit la langue courante depuis `settings.json` (sans cache pour supporter le changement de langue à chaud)
2. Charge le dictionnaire correspondant (avec cache par langue)
3. Retourne la traduction ou la clé elle-même si absente (jamais d'erreur)

Ce comportement de fallback sur la clé garantit que l'interface reste lisible même si une clé est manquante dans un fichier de traduction.

---

## Changement de langue

`set_lang(lang)` écrit la nouvelle langue dans `settings.json["ui_lang"]` sans toucher aux autres clés. Le changement prend effet après rechargement de la page (`ui.navigate.reload()`).

`get_lang()` relit le fichier à chaque appel pour supporter ce rechargement sans nécessiter de redémarrage du serveur.

---

## Règle absolue

Ce module ne touche jamais aux instructions personnalisées de l'utilisateur (`settings.json["prompts"]`, `persistent_context.txt`). Il ne gère que les chaînes d'interface.

---

## Ajout de traductions

Pour ajouter une nouvelle clé traduite :
1. Ajouter la clé dans `data/i18n/ui_fr.json`
2. Ajouter la même clé dans `data/i18n/ui_en.json`
3. Utiliser `t('ma_nouvelle_cle')` dans le code

Si la clé n'est pas encore dans les fichiers JSON lors d'un test, l'interface affiche la clé brute — comportement intentionnel pour détecter les manquants.
